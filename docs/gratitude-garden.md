# Paca’s Gratitude Garden

The garden lives at `/paca-village/holiday/gratitude-garden/` in the existing portfolio. The gingerbread cottage is the ninth stop on `/paca-village/` and opens Paca’s Holiday Village at `/paca-village/holiday/`. Its garden illustration, sign, and invitation form one accessible link into the gratitude garden. Panchita’s scarf logo sits above the garden title. Small Paca Village and Home links provide a way back, and the footer returns to the holiday village. Shared gratitude links and metadata use the garden’s own URL. The portfolio is published through its normal GitHub Pages deployment.

The separate notes service is deployed at https://paca-holiday-village.courtneythko.chatgpt.site. Public anonymous participation was explicitly approved. New valid notes are accepted and published immediately. Garden keeper links are removed from the portfolio and service landing page. The old `/keeper` route remains owner-only for legacy records; existing pending/declined tests are not republished. The portfolio uses that hosted service by default; set `NEXT_PUBLIC_PACA_GARDEN_API_URL=http://127.0.0.1:5180` when developing against its local database. The notes service is hosted and deployed separately from this static portfolio.

Implemented: watercolor garden, tappable tree leaves, five selectable styles, anonymous messages and optional names, shared storage with immediate publication, hearts, public community count, mobile note sheets, planting animation, PNG postcard export, pause/reduced motion, writing prompts, live tree growth, decorative milestone unlocks, milestone previews and Christmas teaser. GMI-generated drifting leaves and a planting twirl are included. Page-wide windblown maple, oak and sage leaves sweep across every section, with varied depth, tumbling and synchronized gusts. The Christmas wishing experience is future work. Eight welcome notes are labeled as Paca's notes and do not inflate the community count.

Validation: TypeScript; full Next.js production export using Webpack; backend production build; local API integration tests including concurrent rate limiting; browser planting, reaction and postcard download; mobile 390px viewport with no horizontal overflow and a bottom sheet note reader. The default Turbopack production build stalled in this environment; `npm run build -- --webpack` completed successfully.

The TypeScript include paths now target `src/` so the portfolio no longer attempts to compile unrelated nested apps under `output/` and `sites/`.

## Community growth

The garden now begins with mostly bare branches and fills with layered watercolor foliage as the public community count rises. Two matching full-scene paintings blend progressively from `gratitude-garden-beginning.png` to `gratitude-garden-flourishing.png`; the canopy reaches full density at 250 notes while the real counter continues growing. The original `gratitude-garden.png` is preserved for the village invitation and postcards. The old enlarged duplicate tree and flat decorative leaf overlay have been replaced with the painted foliage.

Milestones add pumpkins at 3, a bench at 10, fairy lights at 25, small alpaca friends at 50, a fountain at 100, and a golden glow at 250. These smaller goals let a new community unlock decorations sooner. Stage labels, previews, progress and the tree’s growth curve share these thresholds. Growth uses the API's `growthTotal`: public notes plus personal cards first opened from another browser identity. The API retains `total` for published notes and adds `sharedCards` for opened cards; the garden shows both in a breakdown. Welcome notes, pending notes, unopened cards, sender previews and repeated opens do not add leaves. The visible page checks for updates every 30 seconds and on returning to the tab. Paused and reduced-motion modes show the same growth without animations.

At 50 notes, three distinct transparent watercolor alpacas join the two original painted alpacas. Their sprite sheet, `alpaca-friends-watercolor.png`, replaces the two small outlined SVG animals. All three new PNGs were made with the built-in image_gen tool; exact prompts and saved source paths are recorded in `docs/garden-watercolor-refresh.json`. Their transparent alpha is retained, and the original garden illustration and Panchita logo are unchanged.

The counter labels gratitude leaves, including zero, and separates public notes from opened personal cards. A successful plant inserts the note as public and returns `total`, `sharedCards` and `growthTotal` in the same D1 batch. The page immediately adds the note and updates the authoritative count, cancels stale reads, exits milestone previews and announces growth. No review is required. Input checks, honeypot, origin validation and the five-per-hour limit remain. Personal card text never enters the public notes feed.

Milestone buttons provide a clearly labeled visual preview without changing the real count or writing any records. “Back to our garden” returns to the live count. `node --test tests/garden-growth.test.cjs` checks growth boundaries, invalid/loading counts, stable positions, and large-community limits.

## Personal thank-you cards

The primary email action is now “Download email with attachment.” It downloads a local `.eml` email file containing the actual postcard PNG bytes as a MIME attachment, the full message, and the complete card link including its growth receipt. It does not open a link-only `mailto:` draft or ask visitors to paste the image. Sender and recipient addresses are left for the mail app. The original PNG remains available separately, and native “Share image & link” is optional.

`gratitudeEmailFile.ts` creates a `message/rfc822` file with multipart/mixed structure, a UTF-8 text body, base64 PNG attachment, CRLF line endings, and folded RFC 2047 subject words. Attachment filenames are fixed, image signatures are checked, and an `X-Unsent: 1` compose hint is included. Some desktop mail apps honor that hint; others open the file as a message and need Send Again/Forward before addressing it. The UI identifies the `.eml` download and desktop-mail requirement. Webmail/mobile draft import and native mail-app behavior are not guaranteed or verified here; the site does not claim universal automatic attachment support or delivery.

The image and complete email file are prepared before the download click, invalidated when the card changes, and kept in browser memory. Object URLs are revoked on cleanup. No email addresses or images are uploaded to the service. Opening the card link, rather than viewing an attachment, is what grows the tree. Tests use Python 3's independent standard-library MIME parser to verify exact attachment bytes, the full growth link, Unicode/header folding, blank recipients, header injection resistance and malformed PNG rejection. Browser QA downloads and parses the real generated email file without opening an email client or sending mail. See [MIME attachment disposition](https://datatracker.ietf.org/doc/html/rfc2183), [MIME body encoding](https://www.rfc-editor.org/info/rfc2045/) and [encoded subject headers](https://www.rfc-editor.org/info/rfc2047/).

The garden's gratitude panel has “Plant gratitude” and “Send to someone” tabs. Each draft survives switching tabs, with arrow keys and Home/End supported. The sending tab embeds the same composer available at `/paca-village/holiday/gratitude-garden/thanks/`. Visitors choose a leaf, enter a recipient and message, optionally sign their name, and preview a watercolor card. They can use their device's share sheet, copy its link into a text or DM, or download a personalized PNG. Recipients can save their keepsake or create a thank-you of their own. The site does not send messages or claim delivery.

The versioned, validated card payload lives in the link's URL fragment. It is not encrypted: anyone with the complete link can read it. Its names and message are not stored in the notes service or displayed in the public garden. Shared links use the production domain; the preview link stays on the current host for local testing. Analytics scripts are excluded from the standalone composer and recipient page, which also use `noindex`, `no-referrer`, and generic link-preview metadata without the personal message. Invalid or incomplete links show a recovery message.

New cards register an anonymous contribution receipt through `POST /api/cards`, sending only a SHA-256 content fingerprint, form timing, honeypot and browser visitor identifier. The service stores a random receipt ID, a digest of the sender identity plus fingerprint for retry deduplication, a hashed sender identity, creation time and optional first-open time. It never receives the card text. The link includes the receipt as an optional `growthId`; older links remain readable but do not retroactively contribute. A valid `POST /api/cards/open` from another browser identity fills the first-open timestamp once, using a conditional update that also handles simultaneous opens. Sender previews are excluded. This is anonymous browser-based deduplication, not verified recipient identity; changing browsers or clearing storage can change the identity. Registration is limited to five new cards per IP per hour, and first opens to thirty per IP per hour. Card creation remains usable if the service fails, with a retry connection option; recipients can retry a failed growth update. A downloaded image alone cannot report that it was opened.

The separate Sites backend adds the schema-only migration `0001_romantic_zombie.sql` for `gratitude_cards`. Its local-only `tests/cards.integration.mjs` checks origin and input validation, registration retries, sender exclusion, concurrent first opens, aggregate counts, public-feed isolation, rate limits, and immediate public-note publication and count updates. All write tests use an isolated local database, not production.

`node --test tests/gratitude-card.test.cjs tests/garden-growth.test.cjs` covers Unicode round trips, input limits, malformed links, allowed leaf colors, production URLs, and growth behavior. Browser checks cover composing, copying a link, opening the recipient view, downloading its PNG, mobile recipient width, and the absence of analytics scripts on card pages. The production export includes the new static route.

Automatic screening cannot prove the absence of singing or humming.
- The current player uses `public/holiday/autumn-lofi-instrumental.mp3`, a new MiniMax Music 3.0 request with the native `is_instrumental: true` flag and `lyrics_optimizer: false`, approved for another $0.15.
